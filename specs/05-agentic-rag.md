# Phase 5 — Agentic RAG

## 1. Purpose

Upgrade the AI Service from a fixed RAG pipeline into an agentic workflow that can decide whether a user question requires:

- expense policy retrieval
- claim data from the Core API
- both policy and claim data
- no external retrieval

The business domain remains Expense Reimbursement.

Primary learning outcome:

> Build a bounded, observable tool-using agent without introducing unnecessary autonomy.

## 2. Business Use Cases

Examples:

1. "What is the hotel limit in Singapore?"
   - policy retrieval only

2. "What is the status of my latest claim?"
   - Core API data only

3. "Why might claim 123 be rejected under policy?"
   - claim data plus policy retrieval

4. "Explain what a reimbursed claim means."
   - may be answered without retrieval if the product chooses to allow static domain knowledge

The agent must not approve or reimburse claims.

## 3. Architecture Delta

Before:

    Query
      |
      v
    Vector Retrieval
      |
      v
    LLM Answer

After:

    Query
      |
      v
    Agent / Router
      |
      +--> Policy Retriever Tool
      |
      +--> Claim Lookup Tool
      |
      +--> My Claims Tool
      |
      v
    Synthesis
      |
      v
    Answer + evidence

A reference implementation may use LangGraph because the workflow should be explicit and testable.

## 4. Initial Tool Set

Keep the tool set deliberately small.

### search_expense_policy

Input:

- query
- optional region
- optional policy type

Output:

- retrieved chunks
- citations

### get_my_expense_claim

Input:

- claim_id

Output:

- claim only if the caller is authorized through the Core API

The tool must pass user identity to the Core API using trusted runtime context.

### list_my_expense_claims

Input:

- optional status
- pagination

Output:

- caller's accessible claims

No raw database access from the AI Service.

## 5. Identity Propagation

The model must never receive a bearer token as natural-language context.

Trusted application code owns credentials.

Conceptual flow:

    User token
       |
       v
    AI Service validates user
       |
       v
    Trusted tool runtime
       |
       +---- delegated request identity
       |
       v
    Core API
       |
       v
    Core authorization

The LLM chooses a capability. It does not choose the caller's permissions.

## 6. Agent States

A minimal graph:

    START
      |
      v
    classify_request
      |
      +--> policy_only
      |
      +--> claim_only
      |
      +--> combined
      |
      v
    gather_evidence
      |
      v
    synthesize_answer
      |
      v
    END

Avoid a free-running planner loop for this phase.

## 7. Routing Requirements

The router must output a structured decision such as:

~~~json
{
  "route": "COMBINED",
  "reason": "The user asks about a specific claim and whether it complies with policy."
}
~~~

Allowed routes:

- DIRECT
- POLICY
- CLAIM
- COMBINED

Unknown output must fail safely to a bounded fallback, not trigger arbitrary tool use.

## 8. Agent Response Contract

Response should include:

- answer
- route used
- citations when policy evidence is used
- claim references when claim data is used
- optional tool execution summary safe for users

Do not expose chain-of-thought.

## 9. Tool Error Handling

The agent must handle:

- claim not found
- authorization denied
- Core API timeout
- policy retriever failure
- empty retrieval
- LLM provider failure

A tool failure must not cause the model to invent the missing claim data.

## 10. Limits

Set hard bounds:

- maximum tool calls per request
- maximum graph steps
- overall request timeout
- maximum retrieved chunks
- maximum model tokens

These limits are operational controls now and become security controls later.

## 11. Example Tool Wrapper

~~~python
async def get_my_expense_claim(claim_id: str, runtime: ToolRuntime):
    # Credentials live in trusted runtime state, not in the tool arguments
    # generated by the language model.
    response = await runtime.core_client.get(
        f"/claims/{claim_id}",
        headers=runtime.delegated_auth_headers(),
        timeout=5.0,
    )

    response.raise_for_status()
    return response.json()
~~~

## 12. Evaluation Changes

Add agent-specific evaluation dimensions:

- route accuracy
- correct tool selection
- tool-call success rate
- unnecessary tool-call rate
- answer groundedness after tool use
- end-to-end latency
- tool-call count

Create labeled cases where the expected route is known.

## 13. Observability Changes

A trace should now show:

    ai.agent.request
      |
      +-- agent.route
      |
      +-- tool.search_policy
      |
      +-- tool.get_claim
      |
      +-- agent.synthesize

Record:

- selected route
- tool names
- tool latency
- tool outcome
- step count

Do not log credentials or hidden reasoning.

## 14. Testing

Required:

- policy-only query chooses policy route
- claim-only query avoids vector retrieval
- combined query gathers both evidence types
- unauthorized claim request remains denied
- Core timeout produces a bounded failure
- missing policy evidence causes abstention rather than fabrication
- step/tool limits are enforced

## 15. Acceptance Criteria

AC-01. The AI Service uses an explicit agent graph or equivalent bounded orchestration.

AC-02. The agent can choose among DIRECT, POLICY, CLAIM, and COMBINED routes.

AC-03. Only the three approved tools are available.

AC-04. Tool credentials are kept outside model-visible arguments and prompts.

AC-05. Core API remains the authorization authority for expense claims.

AC-06. Tool failures do not become fabricated business facts.

AC-07. Every tool call is visible in traces.

AC-08. Agent execution has hard step, tool, token, and time limits.

AC-09. No write/consequential tools exist yet.

## 16. Explicitly Out of Scope

Do not implement:

- MCP
- claim submission through AI
- claim approval through AI
- reimbursement through AI
- hybrid search
- reranking
- multimodal receipt understanding
- long-term memory
- multi-agent collaboration
- arbitrary web search
- shell/code execution

## 17. Definition of Done

Phase 5 is complete when the AI Service can choose the minimum required capability for an expense question and gather trusted evidence without receiving unnecessary autonomy:

    understand request
        ->
    choose bounded route
        ->
    call approved tools
        ->
    preserve user authorization
        ->
    synthesize grounded answer
        ->
    expose observable execution
